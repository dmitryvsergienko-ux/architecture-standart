#### Логика принятия решений

1. **Главный архитектурный сдвиг — отделение онлайн-канала депозитов от АБС.** Перегруженная АБС с вертикально-масштабируемой Oracle БД не выдержит онлайн-нагрузку, поэтому ни Сайт, ни ИБ не должны обращаться к АБС синхронно. Шина событий Kafka и собственная БД (PostgreSQL) у `Deposit Service` дают независимое масштабирование и обеспечивают R3, P3, +R4.

2. **Минимизация подрядных доработок.** Платформа ИБ (.NET Framework 4.5) устарела, подрядчик дорого правит ядро. Новый функционал делается силами банка как отдельный микрофронт `IB Deposit Module`, что закрывает +R6 и S5. Платформа ИБ-монолита остаётся неизменной.

3. **Технологический выбор Java/Spring.** В банке есть две Java-команды: внутри (АБС, 20 чел., часть владеет Java) и у подрядчика (сопровождение системы кол-центра, 5 чел.). Java-стек совместим с Kafka и подходит для микросервисов. Альтернативно рассматривался .NET (под команду ИБ), но он создаёт связку с устаревшей платформой подрядчика и блокирует переход на Kafka — отказались.

4. **Новые БД — PostgreSQL.** Существующие СУБД банка (MS SQL, Oracle) оставляем за legacy. Использовать их для новых сервисов означало бы либо нагружать перегруженную Oracle-АБС (+R5), либо делать новые сервисы зависимыми от MS SQL — лицензионно невыгодно при горизонтальном масштабировании. PostgreSQL — open-source, имеет всё необходимое для финансовых данных, легко реплицируется в HA-конфигурации.

5. **СМС — отдельный сервис, потребляющий события.** Вынесение СМС-уведомлений в отдельный сервис `SMS Notification Service` (а не доработка ядра ИБ) даёт сразу несколько выигрышей: единая точка СМС для всех будущих процессов банка, отсутствие подрядных доработок, отказоустойчивость через Kafka (R5).

6. **Kafka — стратегический выбор.** Постановка явно называет Kafka как перспективную технологию. Несмотря на отсутствие опыта эксплуатации в банке (см. риски), Kafka выбирается на старте MVP, а не «после» — иначе пришлось бы дважды переписывать интеграции.

### **Альтернативы**

**Alt-1. Доработка ядра ИБ-монолита подрядчиком и реализация всего нового функционала внутри ИБ.**
Отвергнуто: высокая стоимость и зависимость от подрядчика; ядро на .NET Framework 4.5 несовместимо с Kafka; конфликтует с +R6 и S5.

**Alt-2. Прямая синхронная REST-интеграция ИБ → АБС для подачи и обработки заявок.**
Отвергнуто: АБС перегружена, масштабируется только вертикально (+R5); требует доработки API АБС под онлайн-нагрузку; нарушает +R4, R3, P3.

**Alt-3. Использовать существующую схему «Система кол-центра → прямая запись в БД АБС» как образец для всех новых каналов.**
Отвергнуто: shared database — антипаттерн; не масштабируется; усиливает связность ИБ ↔ АБС вместо её ослабления.

**Alt-4. Стек .NET для новых микросервисов (под команду ИБ-разработчиков).**
Рассмотрено: команда .NET в банке есть (10 чел. внутри + 10 у подрядчика); .NET 8 совместим с Kafka. Однако перспектива Kafka, наличие большей Java-экспертизы (команда АБС, 20 чел.) и риск ассоциации новых сервисов с устаревшей .NET-платформой подрядчика склоняют выбор к Java. Если на следующих итерациях бизнес решит расширять команду .NET-разработчиков — стек частично может быть пересмотрен.

### **Недостатки, ограничения, риски**

**Недостаток N-1.** Депозитный микрофронт `IB Deposit Module` встраивается в монолит ИБ-подрядчика — есть риск конфликтов при обновлении ядра подрядчиком. Митигация: фиксированный контракт интеграции (HTML-iframe или web-component), регрессионные тесты с подрядчиком.

**Недостаток N-2.** На MVP сохраняется ручной шаг согласования заявки бэк-офисом депозитов (+R7). Это сохраняет узкое место по времени отклика для клиента (минуты-часы вместо секунд). Целевое состояние — автоматизация через 12 мес. — лежит за рамками MVP.

**Недостаток N-3.** Появляется новая БД `Rates DB`, которая фактически дублирует часть функциональности АБС (учёт ставок). На 12-месячном горизонте источником правды о ставках будет либо АБС, либо `Rates Service` — этот вопрос архитектурно не закрыт в MVP.

**Риск R-1.** При неконтролируемом росте онлайн-заявок АБС всё равно может стать узким местом — поток `deposit.applications.approved` в `ABS Adapter` ограничен пропускной способностью АБС. Митигация: backpressure через Kafka consumer-группы, ограничение скорости обработки в `ABS Adapter`, нагрузочное тестирование до релиза.

**Риск R-2.** Подрядчик системы кол-центра должен реализовать Kafka-consumer на своей стороне для обработки заявок с сайта (UC2, UC3). Это может затянуть сроки MVP. Митигация: SLA с подрядчиком, либо буферный сервис банка `CallCenter Bridge`, который пишет в БД системы кол-центра напрямую (тактическое решение, не стратегическое).

**Риск R-3.** Команда банка не имеет опыта эксплуатации Kafka и Kubernetes. Митигация: PoC до старта MVP (2-3 мес.), привлечение внешнего эксперта на 3-6 мес., обязательная документация runbook-ов, обучение команды АБС/ИБ.

**Риск R-4.** Появление 4 новых микросервисов кратно увеличивает поверхность поддержки и требования к мониторингу. Без полноценного APM (Prometheus + Grafana) и централизованных логов (ELK) удерживать SLA 99.9% будет невозможно (R1, S7). Митигация: A11 — мониторинг включён в скоуп MVP, без него релиз не выпускается.

**Ограничение L-1.** Новый клиент банка не может открыть депозит полностью онлайн (+R3, 115-ФЗ KYC). Архитектура учитывает «двухшаговый» процесс: онлайн-заявка → визит в отделение для идентификации.

**Ограничение L-2.** Все ПДн обрабатываются и хранятся на территории РФ (+R9). Это исключает использование зарубежных облачных провайдеров для `Deposit DB`, `Rates DB` и Kafka — развёртываем в собственных ЦОД банка.

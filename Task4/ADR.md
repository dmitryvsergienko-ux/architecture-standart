### **Название задачи:**
Распределение актуальных ставок депозитов в кол-центр банка и партнёрский кол-центр

### **Автор:**
Команда цифровой трансформации розничного бизнеса

### **Дата:**
2026-05-06

---

### **Контекст**

После старта маркетинговой кампании по депозитам ожидается рост входящих звонков от пожилых клиентов, привыкших к телефонной консультации. Нужно обеспечить:

1. **Сотрудникам кол-центра банка** — возможность видеть актуальные ставки депозитов в их рабочей системе.
2. **Сотрудникам партнёрского кол-центра** — то же самое, но партнёр работает во внешней информационной системе и **не может выполнять API-вызовы**: они готовы получать ставки только в виде файлов (например, по SFTP).

Решение строится поверх архитектуры MVP, спроектированной в Task 3: ставки депозитов хранятся в `Rates Service` (Java/Spring + PostgreSQL + Redis), который при изменении ставок публикует событие `rates.updated` в Apache Kafka.

Менеджер БО депозитов публикует обновлённые ставки в Rates Service Web UI. 2. Rates Service сохраняет ставки в Rates DB, обновляет Redis, публикует событие `rates.updated` (полный snapshot) в Kafka. 3. **SFTP Export Service** (consumer Kafka) генерирует CSV-файл и загружает его на SFTP-сервер. 4. Сист. КЦ банка получит свежие ставки при следующем запросе через API. 5. Сист. партн. КЦ получит свежие ставки при следующем pull по расписанию. |

### **Решение**

Архитектура добавляет два потока распределения ставок поверх существующего `Rates Service` (Task 3):

- **Онлайн-поток** для системы кол-центра банка — REST через API Gateway.
- **Файловый поток** для партнёрского кол-центра — новый микросервис `SFTP Export Service` + SFTP-сервер.

#### Ключевые архитектурные решения

| # | Решение | Обоснование |
|---|---|---|
| B1 | **Сист. КЦ банка читает ставки через REST API Rates Service** (через API Gateway). Никакого прямого доступа к АБС или БД Rates Service. | +R4, +R5 (АБС не нагружается); единый канал получения ставок для всех онлайн-потребителей. |
| B2 | **Партнёр получает ставки в виде CSV-файла через SFTP.** Формат CSV выбран как универсальный для legacy-систем (партнёр не имеет универсального парсера JSON). UTF-8 с BOM — для корректного отображения кириллицы в Windows-инструментах. | Постановка («партнёр готов получать в виде файлов»); широкая совместимость. |
| B3 | **Создаётся новый микросервис `SFTP Export Service`** (Java/Spring Boot). Подписан на топик `rates.updated`, генерирует CSV, загружает на SFTP. Изолирован от Rates Service и от файлового сервера. | Single responsibility: Rates Service занимается ставками, SFTP Export — только их выгрузкой. Можно расширять для других файловых выгрузок без изменения Rates Service. |
| B4 | **Событие `rates.updated` в Kafka содержит полный snapshot ставок** (не diff). Это упрощает генерацию файла и делает интеграцию идемпотентной — каждое сообщение полностью самодостаточно. | Партнёру нужен актуальный snapshot, а не история изменений. Diff-сообщения породили бы проблемы синхронизации при пропуске событий. |
| B5 | **SFTP-сервер — в DMZ банка**, аутентификация партнёра по SSH-ключу. Отдельный системный пользователь с chroot на каталог `/partner/rates/`, права только на чтение. | Стандартная защита периметра; контроль доступа на уровне FS, а не приложения. |
| B6 | **Партнёр выполняет pull по расписанию** (e.g. каждые 15 мин) — банк не push-ит файлы партнёру. Файл всегда есть и доступен через симлинк `rates_latest.csv`. | У партнёра нет endpoint, куда push-ить; pull-схема не требует входящего соединения от банка к партнёру (упрощает security review). |
| B7 | **Локальный кэш ставок в Сист. КЦ банка** с TTL 1 час. При недоступности Rates Service оператор видит ставки из кэша + предупреждение «возможно неактуально». | Деградация вместо полного отказа функции — оператор может продолжать консультировать. |
| B8 | **Ретраи и алертинг в SFTP Export Service.** При неудачной загрузке — Spring Retry с экспоненциальной задержкой; алерт в Prometheus через 3 неудачных попытки или при отсутствии выгрузки > 30 мин. | NFR R5 (гарантированная доставка) + S7 из FURPS+ (мониторинг). |

### **Альтернативы**

**Alt-1.** Сист. КЦ банка пишет/читает ставки напрямую в БД АБС (по аналогии с текущим обращением). Отвергнуто: shared DB — антипаттерн (см. Task 3); АБС не нагружаем (+R4, +R5).

**Alt-2.** Партнёр получает ставки через REST API банка с публичным endpoint. Отвергнуто: ограничение постановки — партнёр не делает API-вызовы.

**Alt-3.** Email-рассылка CSV-файла со ставками партнёру. Отвергнуто: нет audit trail доставки, ниже безопасность (содержимое в clear-text у почтовых провайдеров), ручная обработка на стороне партнёра.

**Alt-4.** Прямой публичный REST endpoint Rates Service для партнёра (без API Gateway, отдельный URL). Отвергнуто по той же причине, что и Alt-2 — партнёр не интегрируется через API в принципе.

### **Недостатки, ограничения, риски**

**Недостаток N-1.** **Eventual consistency между Rates Service и партнёрским кол-центром.** Между обновлением ставки в Rates Service и её появлением в UI оператора партнёра проходит до ~17 мин (max 2 мин на генерацию файла + до 15 мин ожидания pull). Митигация: в файле явно проставлять timestamp `actual_from`; оператор предупреждается «ставки актуальны на _момент_».

**Недостаток N-2.** **Появление новой системы (SFTP Server) увеличивает поверхность поддержки** и SecOps-нагрузки (управление ключами, аудит доступа). Митигация: использовать стандартные инструменты (ansible-роли, monitoring runbook), отнести SFTP к существующим перимет-ресурсам банка.

**Риск R-1.** **SFTP-сервер недоступен.** Если партнёр не может скачать файл, ставки устаревают. Митигация: SFTP-сервер развёртывается в обоих ЦОД (R1, R2 из FURPS+); алерт «партнёр не пуллил > 1 ч».

**Риск R-2.** **Rates Service down → Сист. КЦ банка не получает свежих ставок.** Оператор не сможет проконсультировать. Митигация: B7 — локальный кэш с TTL 1 час и UI-предупреждение при использовании stale data.

**Риск R-3.** **Компрометация SSH-ключа партнёра** → утечка списка ставок. Митигация: ставки публичны (это маркетинговая информация для клиентов); пользователь read-only на отдельный каталог; ротация ключей раз в 6 мес.

**Ограничение L-1.** **Партнёр видит только публичные (общие) ставки**, не персонализированные. Это сознательное ограничение: персонализированные ставки — внутренний риск-метрик банка, передавать партнёру нельзя.

**Ограничение L-2.** **Партнёр должен сам реализовать pull со SFTP** (T9). Если у партнёра нет ресурсов на доработку — банк не сможет полностью реализовать кейс. Митигация: предусмотреть в плане работ время для партнёра, договориться о сроках до старта MVP.
